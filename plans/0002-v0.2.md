# 0002 — v0.2: Global search (file find + grep)

A full-screen search view that replaces the browser while open, modeled
on Zed's project search: input fields on top, a large results area
below where every hit shows its full path with a code preview
underneath. Two flavors sharing one component:

- **File find** (`␣ f`) — match file paths/names.
- **Grep** (`␣ g`) — match file contents.

v0.2 ships in two stages: **stage 1 is UI-only with mock data** (design
review checkpoint, same workflow as v0.1 milestone 1); stage 2 wires
the real GitHub queries.

## 1. UX flow

```
Browser
  │  <Space> f  → GlobalSearch (kind = FileFind)
  │  <Space> g  → GlobalSearch (kind = Grep)
  ▼
GlobalSearch (full screen, replaces the browser; modeline stays)
  ┌──────────────────────────────────────────────────────────┐
  │ query            │ scope          │ extension            │  ← field row
  ├──────────────────────────────────────────────────────────┤
  │ src/widgets/list.rs                                  42  │
  │   40  pub fn render(…                                    │
  │   41      let rows = Layout::default()                   │
  │   42          .direction(Direction::Vertical)            │
  │ ratatui/src/terminal.rs                             137  │
  │   …                                                      │
  └──────────────────────────────────────────────────────────┘
```

- Lands with the **query field focused, INSERT mode** — type
  immediately. No live API calls while typing; `<Enter>` is the
  trigger (same rule as the repo search popup, plans/0001 §1).
- **Field row** (top): query · scope · extension. `<Tab>` moves focus
  forward query → scope → extension → results → query;
  `<BackTab>` reverses. Focusing a text field lands in INSERT.
- **Scope field** is a pseudo-input showing the current scope
  (`repo: owner/name` or `global`). `j/k` cycle the scope directly on
  the field; `<Enter>`/`<Space>` opens a centered popup with radio
  items — `(•) current repo`, `( ) all of github` — where **the radio
  follows the cursor live** (`j/k`/`g`/`G` move and apply), `<Enter>`
  commits by closing, `<Esc>` reverts to the pre-popup scope. One
  popup deep, per the design language (plans/0001 §5).
- **Extension field**: free text, one extension without the dot
  (`rs`, `toml`). Maps to the GitHub `extension:` qualifier (stage 2);
  empty = any.
- `<Enter>` in the query field **runs the search** and moves focus to
  the results box. Re-entering the query (Tab) + Enter re-runs.
- **Results box** (the big area): one block per **file** — multiple
  matches in the same file fold into a single block. Path line (left)
  carries a `N matches` badge (right) for grep, the first line number
  for file find. Under the path: preview lines of code, indented, with
  real line numbers; disjoint match regions are separated by a dim
  `⋮`. Preview lines are syntect-highlighted (same highlighter as the
  browser preview, applied once in `App` at injection); the matched
  text gets the `search_match` chip (yellow bg + crust fg, bold —
  Catppuccin yellow, themeable). The selected block's path row gets
  the standard selection treatment (selection_bg + `▌` gutter,
  plans/0001 §5). `j/k` move between hits (not per preview line),
  `J/K` scroll the view freely.
- `/` in the results box opens the usual transient incremental filter
  (SEARCH chip; type filters live, Enter commits, Esc cancels) —
  filters hit blocks by path **and** preview text. Pure local.
- `<Enter>` on a hit → open that file in the editor, read-only, same
  suspend/resume path as the browser (plans/0001 §12).
- `<Esc>`: from an INSERT input → NORMAL; from NORMAL input or the
  scope popup → back one level (popup closes / input unfocuses);
  from results → close the view, back to the browser. The browser is
  untouched underneath — closing restores exactly the prior state.

## 2. Modes & modeline

No new `Mode` variants. The view reuses the existing chips:

| View state | Chip |
|---|---|
| query / extension focused, INSERT | `[INSERT]` |
| query / extension focused, NORMAL | `[NORMAL]` |
| scope field focused / scope popup open | `[BROWSE]` |
| results focused | `[BROWSE]` |
| `/` filter session | `[SEARCH]` |

Hints come from `keymap::hints(mode)` as usual; the view's title /
bottom border carry the field-specific hints
(`tab fields · enter search · esc close`), like popups do.

Context string in the modeline shows the effective query summary:
`grep "Layout" · repo:ratatui/ratatui · ext:rs` or `global`.

## 3. Scope options (stage 2 wiring map)

GitHub code search qualifiers decide the scope list — a gradual
waterfall that defaults from wherever the browser is:

| Radio item | Qualifier added | Enabled when |
|---|---|---|
| current repo | `repo:<owner>/<name>` | a repo is open in the browser |
| current org | `org:<org>` | an org is selected at the top level |
| all of github | none — global query | always |

Default scope waterfalls: repo open → **Repo**, else org selected →
**Org**, else **Global**. Disabled items render greyed and are skipped
by `j/k`. Later candidates (not v0.2): `user:` scope.

## 4. GitHub backend (stage 2, not in the mock milestone)

- **Grep**: `GET /search/code?q=<query>+<qualifiers>` with
  `Accept: application/vnd.github.text-match+json` — response items
  carry `text_matches[].fragment` + `matches[]`, which is exactly the
  preview block (no extra blob fetch for the visible lines). Repo
  scope adds `repo:`, extension adds `extension:<ext>`.
  Code search **requires auth** — anonymous clients get a clear error
  in the view (no 60 req/h tease).
- **File find, repo scope**: no API call — filter the already-cached
  recursive tree (`RepoTree`) by substring over paths. Instant,
  offline, free. Preview = the same lazy blob fetch the browser uses.
- **File find, global scope**: `search/code` with the query matched
  against paths (`path:` qualifier), text-match fragments off
  (`path:` hits return the file, previews come from blob fetch on
  selection).
- Results reuse the worker-thread + mpsc + generation-counter
  machinery (plans/0001 §6) — one in-flight search, stale dropped.

## 5. Component design (stage 1 — this milestone)

New `src/components/global_search.rs`, one `GlobalSearch` component
parameterized by `SearchKind { FileFind, Grep }`:

- Fields: `query: VimInput` (modal), `extension: VimInput` (modal),
  `scope: Scope` (enum + popup flag), `focus: Focus`, results list +
  selection, transient `/` filter `VimInput`.
- Mock data lives in `global_search.rs::mock` (per the v0.1
  convention): a handful of hits with full paths + 3–5 preview lines
  each, different shapes per kind (file find: query-matching paths,
  preview = file head; grep: preview = lines around the "match").
  Mock enters through the same `update(&Action)` path the real backend
  will use, so stage 2 swaps the producer, not the component.
- Reuses: `VimInput`, the popup shell pattern from `search_popup.rs`
  (centered rect + `Clear` + rounded border + title/hint), `Pane`'s
  `fit()` width truncation rules, `sanitize` for anything that will
  become network-derived.
- Renders into the browser's Rect (full screen minus modeline);
  `App` owns `search_view: Option<GlobalSearch>` and renders it
  **instead of** the browser when `Some`.
- Keys registered in `src/keymap.rs`: leader table gains
  `f` → `Action::LeaderFileFind`, `g` → `Action::LeaderGrep`
  (hints derive from the same table). In-view keys are owned by the
  component, same as `SearchPopup`.
- New actions: `LeaderFileFind`, `LeaderGrep`, `CloseSearchView`,
  `GlobalSearchSubmitted { kind, query, scope, extension }`,
  `GlobalSearchResults { hits }` (mock-injected for now).
- Editor on a hit: stage 1 materializes the mock file bytes via
  `editor::materialize` into a `mock/<kind>` slug dir and opens the
  resolved editor read-only — the full suspend/resume path is
  exercised against real content, so stage 2 only swaps the bytes.

## 7. Open questions — resolved during the mock review

- Extension field: **single extension, free text, dot optional**
  (`rs` / `.rs` both fine). Multi-extension would need OR queries —
  not worth it.
- `<Enter>` from the extension field **also runs the search** — every
  text field submits.
- Preview size: **fixed per mock entry (3–5 lines)**; stage 2 takes
  whatever the text-match fragment gives, capped at 5.
